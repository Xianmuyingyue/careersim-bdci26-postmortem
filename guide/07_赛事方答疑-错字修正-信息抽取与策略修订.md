## 一、修正后的文稿

### 1. 总体要求

> 用 JiuwenSwarm 框架把这个 Agent 搭起来，通过赛题提供的 **MCP Server Career-Emulator** 和环境做交互。  
> 参赛者需要熟悉 **openJiuwen** 框架，包括如何集成、使用这些 Skills。
>
> 最终交付的格式需要按照指定的要求。我们期待大家把 Skill 的文件夹按照我们规定的结构打成**单个 zip**。  
> 在 manifest 里面要选好运行模式，可能是 `agent`，也可能是 `team`。  
> 如果是多 Agent 协同的话，就要按照 **Swarm Skill** 来组织。

### 2. 赛题目标

> Agent 需要明确一个目标，也需要看懂达成这个目标的过程中**坑在哪里**。  
> 目标是清晰的：尽量在 48 个月里**不要出局**，跑到最后的结算环节，并尽量优化各个维度的指标。

### 3. 不完全信息披露 —— 最关键的一条

> 赛题设计做成的是**不完全信息披露**。公开的只是框架和一些具体的规则方向，  
> 但细节——比如**晋升的阈值是多少、绩效的公式**——我们不做披露。
>
> 这意味着 Agent **不可以只有背手册的能力**，还需要：
>
> - 读懂系统给出的**自然语言反馈**
> - 和系统做**有效交互**
> - 会**翻日志**
> - 会从**暗示和历史轨迹**里摸索出隐藏的机制

### 4. 决策节奏

> 节奏是：**月度 / 季度 / 半年度**。  
> **每个月月初**会发一笔基本工资到 Agent 的财富指标，也是在这个时候系统生成具体事件。  
> 每个月**最多 3 个事件**，Agent 需要根据系统给出的背景做选择。  
> 这个选择既会短期改变各维度指标，也会影响后面的事件走向。
>
> **季度末**：Agent 会拿到 **3 点能量值**，可以用来做加班、学习、人脉积累或修复等等。  
> 注意：**用不完不可以累积**。  
> 每个季度末还可以**额外选择 1 个季度主行动**，可以选择做项目、做汇报、做避险，也可以选择不行动。
>
> ⚠️ 需要注意：**体力行动有副作用**。比如选择「高强度工作」，产出会增加，但代价是健康值减损。
>
> **每 6 个月**：一次绩效评估，据此发放绩效奖金；同时开放**晋升窗口**。

### 5. 晋升与长期性

> 职级从 L1 到 L10。晋升主要看**综合指标**（Skill / Network / Output 这一类需要长期经营的指标）。  
> 不是某一个月六个维度特别好就一定能晋升成功，**是看长期综合加权的结果**。
>
> 还有一点很关键：**很多风险不会在当月及时爆发**，而是攒到一个阈值去做处罚。  
> 所以设计 Agent Skill 时要注意：**这是长期规划题，不是单步贪心题**。

### 6. 状态面板与资源分配

> 系统会在 Agent 每次做出选择时，在终端/Web 打印**六个维度的现状**。
>
> 有些指标值得不断积累拔高，比如**职级和财富**；  
> 有些指标只要**不降到触发淘汰的阈值**就可以，比如**健康值**。
>
> 策略上：**不要把所有资源砸向同一个维度**，做单向暴力优化**一定会被淘汰**；  
> 但也**不要摆烂某些维度**，比如健康值、尊严值，也需要权衡好。

### 7. 交付物要求

> 交付目录里必备：
>
> - `manifest.json`
> - `README.md`
> - `design/` 文件夹 —— 放文本，讲清楚 Agent **Skill 设计的思路**
> - `skills/` 文件夹 —— 最终开发的 Skill，可以一个或多个
>
> 交互上常用的 **5 类 MCP**：`new_game` / `observe` / `take_action` / `show_employee_handbook` / `check_latest_logs`。

### 8. 评分与失败

> 活满 48 个月，系统按**六个维度**量化结算，本地模拟器算量化部分，**比重较重**。  
> **策略的工程质量和资源效能**，由云端评测做补充。最终等级 **S 到 E**。
>
> 显著的失败方向：
>
> - 健康值归零 → 强制结束
> - 长期无尊严 → 危机
> - 隐患持续累积 → 爆雷
> - 长期低绩效 → 出局
> - 人脉关系长期归零 → 危险
>
> 这些方向是公开的，**精确的阈值不公开**，需要大家在比赛中体会红线在哪里。

### 9. 两条总结性提醒

> **① 不要做单向的暴力优化。**  
> **② 把自然语言反馈当做线索，而不是背景文案——它有可能是有意义的。**

## 三、★ 新的可用机制信息（此前未充分利用）

### 3.1 每月工资播报携带职级

`monthly_flow` 第 1 步「月初发放当月基本工资」，观测到的原文格式：

```
本月基本工资到账：+0.7（L4）
本月基本工资到账：+0.5（L3）
```

**⇒ 这是一个免费的职级/财富双重读数**，可用于：

- 校验当前职级（不必依赖 `level` 字段）
- 反推本月是否已生效晋升
- 校验财富累积节奏是否落后计划

月薪表：`L1 0.3 / L2 0.4 / L3 0.5 / L4 0.7 / L5 1.0 / L6 1.5 / L7 2.3 / L8 3.6 / L9 5.7 / L10 9.1`  
半年奖金：`S ×3.0 / A ×1.5 / B ×0.5 / C ×−1.0 / D ×−2.0`（基础月薪 × 系数）

### 3.2 ★ 职级截断是「天花板」，不是「护栏」——晋升是唯一解锁变量

`stat_clamp`：在职级 L，`skill / network / output` 上限 = **`int(下一级门槛 × 1.2)`**。  
（源码 `game.py:353`：`caps[stat] = int(condition.threshold * clamp_factor)`，用 `int()` **截断**、按 `from_level` 键控；`clamped_stats = [skill, network, output]`。`clamp_factor=1.2`。）

**★ L3 起的完整截断表（含下一级门槛与余量）**

| 在职级 | skill 上限 | output 上限 | network 上限 | 下一级门槛 (S/O/N) | 截断余量 (S/O/N) |
| --- | --- | --- | --- | --- | --- |
| L3 | 42 | 16 | 21 | L4 需 35/14/18 | +7 / **+2** / +3 |
| L4 | 108 | 26 | 36 | L5 需 90/22/30 | +18 / +4 / +6 |
| L5 | 156 | 38 | 54 | L6 需 130/32/45 | +26 / +6 / +9 |
| L6 | 204 | 54 | 72 | L7 需 170/45/60 | +34 / +9 / +12 |
| L7 | 252 | 72 | 96 | L8 需 210/60/80 | +42 / +12 / +16 |
| L8 | 300 | 90 | 120 | L9 需 250/75/100 | +50 / +15 / +20 |
| L9 | 348 | 108 | 144 | L10 需 290/90/120 | +58 / +18 / +24 |

> 附（L3 之前，供对照）：**L1 = 9/3/3**、**L2 = 21/6/7**。L1 的 O/N 截断余量为 **0**（上限 3 = 门槛 3），任一维掉下去就卡死。  
> ⚠️ 修正：原稿把 L5 的 output 上限写成 **38.4**，源码实际取 `int(32×1.2)=38`（截断）。不影响可达性判断。

**⇒ 每一级的三项门槛都低于其截断上限，L8/L9 在设计上都可达，卡点只在积累速度。**  
**⇒ 最紧的一格是 L3 的 output：上限 16 只比 L4 门槛 14 高 2 点**——L3 阶段 output 顶到 16 还不够就要立刻升 L4 解锁，否则 6 个月干烧。  
**⇒ 反面推论：晚升一级，就把三项的上限锁死 6 个月，损失无法追回。这坐实了「极限抢晋升」。**

### 3.3 「不要单向暴力优化」的机制解释

这句话不是道德劝告，它有两条硬机制支撑：

1. **绩效公式的 softcap**：`低/高 = min/max(Skill, Network)`，超出 2 倍的部分只按 **30%** 计入  
   ⇒ 只堆 skill 会让绩效分被系统性打折 → 奖金档位下降 → 财富下降
2. **截断机制**（见 3.2）：单项堆到上限后，**投入 100% 归零**  
   ⇒ 必须先升职才能继续涨

### 3.4 失败线的精确重述（与转写的"客气说法"对照）

| 转写说法     | 引擎精确条件                          | HP            |
| -------- | ------------------------------- | ------------- |
| 健康值归零    | `health <= 0`                   | **1（唯一一击必杀）** |
| 长期无尊严    | `dignity <= 1` 连续 3 个月          | 2             |
| 隐患累积     | `hidden_risk >= 5` 爆雷；**第二次出局** | 2             |
| 长期低绩效    | **连续两次半年绩效 <4**（不是"绩效 D"）       | 2             |
| 人脉归零     | `network <= 1` 连续 3 个月          | 2             |
| （未提）财富赤字 | `wealth <= 0` 连续 3 个月           | 2             |
| （未提）技能淘汰 | `skill <= 0`                    | 5             |

> ⚠️ 引擎原文为 **`performance_score < 4`**，手册的说法是"连续两次拿 D"。  
> **以源码 `<4` 为准**——即 C 档（约 3 分）也算，比手册描述更严格。

## 四、★ S 级（≥90 分）可行性测算

### 4.1 情景推演（按官方月薪/奖金/归一化公式精算）

| 情景                | 总分        | 等级      | 财富           | skill | network | 风险 |
| ----------------- | --------- | ------- | ------------ | ----- | ------- | -- |
| 现状最佳（L6@48，实际跑出）  | 69.46     | B       | 38.8         | 143   | 57      | 4  |
| L7@36 + 全 A 档     | 84.90     | A       | 71.6         | 175   | 62      | 1  |
| L7@36 + 后期 S 档    | **88.00** | **A**   | 81.9         | 175   | 62      | 0  |
| **L8@42 + 全 A 档** | **91.00** | **S ✓** | 85.1         | 215   | 82      | 0  |
| L8@48 + 全 A 档     | 89.84     | A       | 75.3         | 215   | 82      | 0  |
| 理想上限（L9@48 全 S）   | 94.00     | S       | 110.4（截断 80） | 250   | 120     | 0  |

**核心结论：**

- **L7 路径的天花板约 88 分，拿不到 S。**
- **L8 是 S 级的必要条件**（L8@42 → 91.0；L8@48 → 89.84，差 0.16 分）。
- 财富这条线在 L8 + 全 A 档时已达 85.1（超过上限 80，会被截断）⇒ **财富不是瓶颈，职级才是。**

### 4.2 L8 的积累速度要求

扣除 16 次主行动（全投「申请关键项目」= Skill+16 / Output+32 / Network+16）后，仍需：

| 指标      | L8 门槛 | 缺口  | 需每月  | **需每个剧情选择** |
| ------- | ----- | --- | ---- | ----------- |
| skill   | 210   | 194 | 4.62 | **1.54**    |
| output  | 60    | 28  | 0.67 | 0.22        |
| network | 80    | 64  | 1.52 | 0.51        |

（全局约 48×3 = 144 个月度事件，扣除体力/主行动回合约 126 个剧情选择）

**⇒ 唯一硬骨头：skill 必须做到平均每个剧情选择拿到 +1.54。**  
我们目前最佳局 skill 143 ≈ 每个选择 +1.0。**需要提升约 50%。**

## 五、策略修订建议（针对冲击 90+）

### 修订 1：把「铁律 3」从 120 改为「下一级晋升门槛」——**这是冲 L8 的前提**

现行「`skill >= 120` 停投」会**把 skill 卡在 120，永远到不了 L8 的 210**。  
新规则：**skill 达到下一级门槛 + 安全余量后，才把增量资源转向 output/network。**

### 修订 2：主行动 16 次全部锁定「申请关键项目」

主行动**零副作用**（§2.1 已确认），而「申请关键项目」是唯一同时给 `Output+2 / Skill+1 / Network+1` 的动作。  
当前执行率仅 55/126 = **44%**，「申请岗位轮岗」占了 34 次（Output +0）。

⇒ 改判：仅当 output 已达「下一级门槛 × 0.9」且 skill 是唯一缺口时，才允许轮岗。

### 修订 3：「健康值够用即可」——量化为 `health ∈ [4, 6]` 的目标区间

官方明示 health 不必堆高，且 11 局数据支持（`resilience` 在存活组内 r = −0.108）。  
但 health 归零是唯一一击必杀，**且初始 health 可能只有 5**。

⇒ **目标区间：稳定维持 `health ∈ [4, 6]`，低于 4 才用「健康恢复」回补，绝不主动超过 6。**  
释放出来的体力全部投向「准备汇报材料」（Output）与「处理历史埋雷」（风险）。

### 修订 4：把「每月工资播报」接入局势快照

在 `situation-awareness` 的第六步输出格式里，**增加解析工资播报行**：

```
本月基本工资到账：+X.X（LN）
```

用途：校验职级、确认晋升是否生效、核算财富是否落后于计划轨迹（目标见 §4.1）。

### 修订 5：建立「晋升倒计时表」，按 L8@42 倒推

目标里程碑（每个评审窗口都要升）：

|   | 窗口   | 目标职级 | 门槛 (skill/output/network/dignity) |

|   | 月 6  | L2   | 8 / 3 / 3 / 2                     |
|   | 月 12 | L3   | 18 / 5 / 6 / 3                    |
|   | 月 18 | L4   | 35 / 14 / 18 / 3                  |
|   | 月 24 | L5   | 90 / 22 / 30 / 4                  |
|   | 月 30 | L6   | 130 / 32 / 45 / 4                 |
|   | 月 36 | L7   | 170 / 45 / 60 / 5                 |
|   | 月 42 | L8   | 210 / 60 / 80 / 5                 |
