# 01 · 赛题全解与技术路线

## 一、题目要你做什么

### 任务陈述

> 基于 **openJiuwen 社区 JiuwenSwarm 框架**，编写 **Agent Skills**，开发一个能够在复杂动态职场环境中**长期运行**的「职场打工模拟 Agent」。
>
> Agent 在持续 **48 个月** 的动态组织环境中，通过读取工作邮件、会议纪要、领导反馈、同事消息、组织公告等**自然语言信息**，完成长期规划、月度行动决策、风险控制、绩效提升与晋升路径管理。
>
> Agent **无法直接观察全部真实组织状态**，需在**不完全信息**下推断环境变化，并在健康、尊严、专业能力、人脉、绩效、财富与风险之间做**长期平衡**。

### 考察重点（官方原文）

1. 基于特定任务进行**经验的记录与分析**
2. **构建、优化长期任务 Agent Skills** 的能力
3. 提示词与 **Agent 行为模式调优**
4. **多 Skill / 多 Agent 协同**
5. **上下文管理**
6. **长期规划**
7. **风险管理与资源效率**

### 一句话抓住本质

这不是"写提示词让模型聪明一点"，而是**把一套可复用、可校验、可演进的长程决策工程沉淀成 Skill**。模型固定为 DeepSeek-V4.1-Flash，**唯一变量就是你的 Skill 工程质量**。

## 三、技术路线（四层架构）

```
┌─────────────────────────────────────────────────────────────┐
│  L4  交付层  solution/  →  zip                                 │
│      manifest.json · README · design/ · skills/               │
├─────────────────────────────────────────────────────────────┤
│  L3  技能层  Agent Skills（这是你真正要"开发"的东西）            │
│      ┌──────────────┬───────────────┬─────────────────┐      │
│      │ 局势感知      │  风险控制      │   决策策略       │      │
│      │ (事实层)      │  (约束层)      │   (决策层)       │      │
│      │ 只描述不评价   │  只否决不选择   │  在约束内优化     │      │
│      └──────────────┴───────────────┴─────────────────┘      │
│              ▲ 每回合三段式流水线，见 skills_design.md          │
├─────────────────────────────────────────────────────────────┤
│  L2  编排层  JiuwenSwarm  Agent                                │
│      mode: agent / team · 任务规划 · 子代理编排 · 技能演进       │
│      上下文瘦身 · 分层记忆                                      │
├─────────────────────────────────────────────────────────────┤
│  L1  环境层  career-emulator MCP（5 个工具）                    │
│      new_game · observe · take_action                          │
│      show_employee_handbook · check_latest_logs               │
└─────────────────────────────────────────────────────────────┘
```

### 每回合的控制流

```
observe(session_id)
   │
   ├─▶ [situation-awareness]  解析状态 → 结构化快照 + 红线余量 + 窗口倒计时
   │
   ├─▶ [risk-guardian]        输出硬约束（禁止条件）+ 建议补救
   │
   ├─▶ [decision-policy]      在约束内选择 choice 编号
   │
   └─▶ take_action(session_id, choice, notes=理由)
                                    │
                                    └─ notes 写入日志 → 可复盘、可评审
```

**为什么这样分层？** 三个理由：
1. **可调试** — 三类问题（解析错、规则严、策略差）可分别定位。
2. **可演进** — JiuwenSwarm 的技能演进按 SKILL 粒度优化，粒度越细噪声越小。
3. **抗上下文截断** — 把"不变量"（阈值、公式、动作库）放在 SKILL.md 里，每回合重新载入，而不是依赖对话历史。

## 四、Skill 设计方法论

### 4.1 一个 SKILL.md 的规范结构

```markdown
---
name: your-skill-name          # 必填，kebab-case，通常与目录名一致
description: 一段说明…          # 必填；要写清"做什么 + 什么时候用"
---                            # 前面必须是文件第一行，否则校验失败

# 标题

## 何时使用 / 触发条件
## 输入（从哪读数据）
## 处理规则（判据 + 阈值 + 动作库）
## 输出格式（固定模板）
## 禁止行为 / 边界
```

**校验规则（`career_sim_runner` 实际执行的）**：
- 文件必须以 `---` 开头，且存在闭合 `---`
- frontmatter 必须是合法 YAML
- 必须含非空的 `name` 和 `description`
- 每个技能必须是 `skills/<目录>/SKILL.md`，目录名即技能 id

### 4.2 能力划分的推荐切法

按 **职责正交** 而非"按流程顺序"切分：

| 好的切法（本项目采用） | 差的切法 |
| --- | --- |
| 事实层 / 约束层 / 决策层 —— 各层可独立替换 | 「第一季度策略」「第二季度策略」—— 内容重复且无法复用 |
| 每个技能只管一件事，边界清晰 | 一个巨型 SKILL 包打天下 —— 无法演进、无法调试 |
| 规则基于**状态与阈值**，可跨剧本迁移 | 规则基于**具体事件 ID / 台词** —— Dev 上高分，Test 上归零 |

### 4.3 官方给出的技能拆分建议（原文）

> - 一个 SKILL 负责读取状态与日志，整理局势。
> - 一个 SKILL 负责做短中期策略判断，平衡健康、尊严、产出和人脉。
> - 一个 SKILL 专盯风险和失败方向，避免队伍打着打着突然学会了什么叫职业生涯自由落体。

本提交的 `situation-awareness` / `decision-policy` / `risk-guardian` 与之**一一对应**，并额外强化了"约束层对决策层有否决权"这一设计。

## 五、多 Agent 协同（可选）

若采用 `mode: team`（Leader 统筹拆解 + Teammate 按角色并行），须遵循 **Swarm Skill 标准**：
`官方资料/Swarm-Skill标准-2605.10052v2.pdf`

**但请注意权衡：**

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| `mode: agent`（单 Agent） | Token 效率高、延迟低、上下文单一 | 复杂风险场景的推理深度有限 |
| `mode: team`（多 Agent） | 角色化并行、可做"红队/蓝队"对抗式审议 | Token 开销显著上升，**而资源效能是评分维度** |

**建议**：先用 `agent` 模式把基线做扎实，再评估 `team` 模式带来的分数提升是否配得上 Token 成本。

## 六、提交与迭代闭环

```bash
# 开发循环
make sync            # 装依赖
make setup           # 配实例 + MCP + 环境变量
make start-jiuwen    # 起服务（独立终端常驻）
make play            # 挂载 solution/ 并跑一局
make score           # 读结局分
make replay          # 从 events-*.jsonl 生成 Markdown 战报
```

**单次提交配额**：每日每队最多 1 次（云端初赛提交）。因此**本地必须充分验证后再提交**。

**运行产物位置**（用于复盘）：

```
.career_sim_runner/career_emu/outputs/<submission_name>/<timestamp>/
  transcript-*.log      # 完整对话记录
  events-*.jsonl        # 结构化事件流（可被 replay 解析）
  score_report.json     # 结局评分报告（含各维度得分与 Token 用量）
```

**迭代方法**：`make replay` 生成战报 → 定位失分点（哪条红线被逼近？哪个季度决策低效？）→ 回写 SKILL.md → 再跑一局。**每次只改一处，避免无法归因。**

## 七、常见失分点（避坑清单）

| # | 失分点 | 正确做法 |
| --- | --- | --- |
| 1 | 硬编码 Dev 事件内容 → Test 归零 | 规则基于状态与阈值，不引用具体事件 ID/文案 |
| 2 | 忽略 Token 成本 | 快照用固定短模板；不每回合刷日志；不做多轮自我辩论 |
| 3 | 上下文膨胀导致早期约束丢失 | 把不变量写进 SKILL.md，每回合重新载入 |
| 4 | 只优化收益不做风险约束 | 风险必须做成"硬约束层"，不能是收益函数里的权重 |
| 5 | 技能写得像论文说明 | SKILL 里只留「判据 + 阈值 + 动作库」，解释放 design/ |
| 6 | 未提交 `design/` 文档 | 专家评审 30% 直接依赖它，必须写清设计/规划/风险/恢复/资源优化 |
| 7 | 团队名留占位符 | `manifest.json` 的 `team` 不得为空或 `enter your team name here` |
| 8 | 二次调用 `new_game` | 竞赛模式只允许一局；已有 session_id 必须复用 |
| 9 | 违规使用外部数据/小号 | 直接取消成绩并公示 |
| 10 | 未在截止前完成组队 | **2026-09-30 12:00 截止报名组队**（PC 端操作） |
