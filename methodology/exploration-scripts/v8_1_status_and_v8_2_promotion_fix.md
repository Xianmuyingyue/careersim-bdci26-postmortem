## 一、指令7 的诊断：前 3 次晋升为什么守不住

### 1.1 v8 批次晋升时间线（4/4 实测）

| 局 | 职级路径 | 漏掉的窗 |
| --- | --- | --- |
| RUN1 | [1L1, 6L2, 12L3, 24L4, 42L5] | **M18 L4**（延到 M24） |
| RUN2 | [1L1, 6L2, 18L3, 24L4] | **M12 L3 + M18 L4** |
| RUN3(A) | [1L1, 6L2, 12L3, 24L4, 42L5] | **M18 L4** |
| RUN4 | [1L1, 6L2, 12L3, 24L4] | **M18 L4** |

结论：
- **M6 L2：4/4 全部守住**（L1→L2 门槛极低，且 O/N 在 L1 余量为 0 只能"守"）。
- **M18 L4：4/4 全部漏掉**（最一致的缺陷，连 A 级局都漏）。
- **M12 L3：RUN2 漏掉一次**（偶发）。
- 引擎机制：漏一窗 = **永久 −3.0 职级分 + CAP 锁死 6 个月**（长尾惩罚，正是用户说的"晋升后长尾效应明显"的反面——不晋升则长尾被锁死）。

### 1.2 根因（从 RUN3 回放精确定位）

L3→L4 门槛 `skill 35 / output 14 / network 18 / dignity 3`，但 L3 的截断上限是 `skill 42 / output 16 / network 21`。
M12 晋升 L3 后吃快晋升税（network −3 / dignity −1），窗口起点约 `S18 O5 N3 D2`。
要在 M13–M17（仅 1 个行动季 M15 + 5 个剧情月，零行动预算的 M16–17 是暴露窗）凑齐：

- output：5 → 14（**+9，CAP 仅 16，几乎无超额缓冲**）
- skill：18 → 35（+17）
- network：3 → 18（+15，含税恢复）

**RUN3 在 M15 冲刺月的实际状态：`H7 D10 S27 N11 O10`**，output 仍是瓶颈。
它的决策（回放原文）：
> "that leaves O at 13, one short of 14… monthly events will add output too (some events give output+). So O13 + 2(energy) + 2(events) = 15 ≥ 14."

即把 output 停在 **13（差阈值 14 一点）**，并**赌隐藏剧情事件会补上缺口**——结果剧情没给 output，M18 直接漏到 M24。

这同时踩了三个坑：
1. **未把 output 顶到 CAP(16) = 阈值+2**：违反铁律1 的余量 ≥+2 安全线（余量标定 +1→80%、0→62%、<0→39%）。
2. **把 1 点体力浪费在「健康恢复」**：当时 `health=7`，健康恢复记 0 分（铁律7），属纯浪费（铁律14 零浪费的反例）。
3. **依赖"剧情可能增益"补缺口**：暴露窗 M16–17 零行动预算，若剧情带 ΔO<0 会把已顶到的 output 打下来，且无法补救。

### 1.3 为什么是 output 而不是 skill/network

`situation-awareness` §5.6 分层普查（20 局 × 8 评审边界）：**L3→L4 未通过的短板构成 = output 81% ＞ skill 12% ＞ network 6%**。
机制：output 在 L3 的 CAP 仅 16（=阈值 14+2），**是所有维度里"超额缓冲最小"的**——
skill 有 42（超 35 共 7 点）、network 有 21（超 18 共 3 点），唯独 output 几乎贴着阈值。
任何剧情方差（ΔO<0）都会直接把 output 打到阈值以下，而它又无法提前"囤"（封顶 16）。
⇒ output 必须**在 M15 顶满到 16** 且 **M16–17 严守铁律12 不扣 O**，才能稳过。

2. `decision-policy` §六 L3→L4 行：改写为"output 从 M13 全密度推进、M15 顶到 16、M16–17 不扣 O、顶满前禁选轮岗/健康恢复"。
3. `decision-policy` §六 新增「前 3 次晋升硬防御（铁律15 执行协议）」小节（三原则 + 自检锚点）。

5. `situation-awareness` §七 快照：新增"前3防御"自检行。

### 2.2 铁律15 三条执行原则

1. **冲刺月 M(6k−3) 四维必须到 `TH(next)+2`（或 CAP），且不得依赖隐藏剧情增益补缺口**。
   余量标定：≥+2→100%／+1→80%／0→62%／<0→39%。
2. **M18 特别条款（output 81% 瓶颈、CAP 仅 16）**：L3 窗口（M13–M17）output 享最高优先级——
   output 未达 16 前：① 主行动禁选「申请岗位轮岗」(skill，其解锁线 output≥12.6 仍低于 L4 阈值 14)；
   ② 体力禁选「健康恢复」（health≥7 记 0 分纯浪费）；③ 每季主行动优先「申请关键项目」(+2 O)；
   output 顶满后才轮到 `skill`(→35)/`network`(→18+2)。
3. **M16–17 暴露窗严守铁律12**：只选 ΔO≥0 且 ΔN≥0，绝不把已顶到的 output 打下来。

### 2.3 与现有算法的兼容性

- `先易后难`（§2.2③）在 L3 窗口本就因 `g(output)` 最小而优先 output，铁律15 只把它**硬化**（不许中途倒给健康恢复、不许赌剧情）。
- §三「申请岗位轮岗」的解锁条件 output≥12.6 被铁律15 的"output=16 才解锁"**收紧**（铁律15 优先级更高，直接覆盖）。
- 不与其他铁律冲突：output 推进是低风险动作，不与风险否决（铁律5/6）矛盾；health≤5 时铁律6 仍优先（铁律15 仅禁"零价值"的健康恢复）。

## 四、v8.2 总体节奏策略（用户补充，三段）

用户在铁律15（前 3 硬守）之外，补充了**总体节奏**：前 3 守完后进入**调整期**，**中间 4 个晋升机会保 2 争 3、稳住健康与风险**，最后周期在风险有余量时**故意激进暴雷一次冲 M48**。

### 4.1 三段划分（已写入 铁律16 + 约束5f）

| 阶段 | 窗口 | 目标 | 执行要点 |
| --- | --- | --- | --- |
| **一 M1–M18** | M6 L2 / M12 L3 / M18 L4 | 硬守 3/3（铁律15） | 前 3 最容易且长尾效应最大；漏一窗 = −3.0 职级 + CAP 锁死 6 月 |
| **二 M24–M42** | M24/M30/M36/M42（4 窗） | **保 2 争 3** | 不再强求每窗晋升；优先稳住 `health` 与 `hidden_risk`，允许跳过 1–2 窗激进冲刺，资源留给阶段三 |
| **三 M42–M48** | M48（终局一窗） | 有余量则故意激进一次 | `hidden_risk ≤ 2` 且 `R̂ ≤ 2`、非爆雷冷静期、`health > 3` 时，可为 M48 晋升主动推高 risk 触发**单次**暴雷（约束5f 放行） |

### 4.2 为什么"保 2 争 3"而非"每窗必升"

中段（M24–M42）每漏一窗虽丢 −3.0 职级，但若为强升把 `health`/`hidden_risk` 推到边缘，反易后段暴雷或健康崩盘（一击必杀）。中段以"稳"为主，确保进阶段三时 `health` 高、`risk` 低，才有资本终局激进。
⇒ 这**松弛了**原先 铁律13 的"每窗必升"硬目标（铁律13 改为"参考目标线"，实际执行以铁律16 为准）。

### 4.3 阶段三的算术（故意暴雷为何划算）

- M48 晋升 ≈ **+3.0 职级 + 财富联动**（月薪跳档 + 可能 S/A 奖金）。
- 单次暴雷代价 = `output` 回写 6 个月前 + `D−2` + `W−2` + talk −4.0（约 −1.0 风险维 + 少量财富/尊严）。
- **净收益为正**，且 M48 是终局月：**单次暴雷不会二次出局**（hp=2，需 2 次才死，无"下一窗"），暴雷后 `risk` 归 0 反而利于 talk good。
- **永不放松**：`health≤3` 一击必杀（铁律6 / 约束1）、暴露窗 N/O 保护（约束11，M46–M47 仍须守住）。

### 4.4 落点（已写入 solution/）

- `decision-policy`：铁律13 改为"参考目标线"并指向铁律16；新增 **铁律16（三段节奏）**；§六 新增「三段节奏总纲」小节；§六 L3→L4 行 / 铁律15 协议不变（阶段一细节）。
- `situation-awareness`：§5.8 倒计时表加"节奏阶段"列 + 三段节奏注释；§七 快照"前3防御"行不变。
- `risk-guardian`：新增 **约束5f（终局激进豁免）**（仅阶段三 + 有余量 + 非冷静期 + health>3 时放宽 risk 注入否决），并排入 裁决顺序（位于约束11 之下、约束5 之上，且明确不覆盖 N/O/health 类约束）。
