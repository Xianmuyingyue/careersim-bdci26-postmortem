## 一、复盘判读：两个必须纠正的解读 + 三个确认的结论

### ★ 判读 1（纠正）：「v3 均值 65.30 > v7 57.38」不构成 v3 更优的证据
- 引擎 `new_game()` **无种子**，两局剧本 Jaccard 重叠率仅 52.8%；跨批均值对比受抽样噪声支配（用户简报亦承认 n=3 噪声范围内）。
- **决定性换算：v7 两局存活局均值 = (62.28+66.83)/2 = 64.56 ≈ v3 的 65.30**。
- ⇒ v7 的全部均值差距来自 RUN 4 一次爆雷死（43.02 拖低 7.5 分）。**两道硬门（M11 生死线+暴露窗）本身几乎零代价**。

### ★ 判读 2（纠正）：「回归 v3 基线」存在物料障碍
- 已核实：git 仓库 `solution/skills/` 只有 `.gitkeep`（v3 文本从未入库）；`analysis/ab/` 只有 arm_A / arm_B / v5 / v6 / v7 五个快照，**无 v3 快照**（v3 走老 explore 驱动批次）。
- ⇒ 「严格回归 v3」需要重建 549 行条文或从历史会话找回，成本高；而判读 1 表明 v3 条文相对 v7 的优势**当前无证据支持**。

### 确认的结论
1. **M11 生死线生效且有机制级证据**：绩效型死亡 v5 的 1 例 → v7 的 0 例，两局通关走满 48 月 ⇒ 保留。
2. **爆雷是唯一未堵住的死因**：RUN 4 死于**第二次**爆雷（M39，L4，财富 12.4）。死因链：首爆 → `output` 回写 6 个月前快照 → 产出缺口重开 → Agent 补产出时选高风险选项 → 风险从 0 重新爬到 ≥5 → 二次爆雷出局。**首爆后的行为修正缺失是根因，不是清理节奏单方面问题**（清理 −1/季 vs 剧情 +3/+5 单次注入，账面确实追不上，但「不接大额注入」本可不对冲）。
3. **n=3 的死因分布与 v5 互不相同**（v5：绩效/爆雷/通关×2；v7：爆雷/通关×2）⇒ 继续遵守「分死因计数」纪律，不做单局归因。

## 三、B 的具体设计：运行时风险记账（v8 新增核心，对症 RUN 4）

### B1 双信号记账
- **信号一（现状保留）**：HR 文案量表即时读数（`笑着=0 / 黄=1 / 橙=2 / 红=3 / 临爆=4`）。
- **信号二（新增）**：**ΔRisk 累计账本**——Agent 对每个选择累计记账 `ΔRisk`（剧情 +1/+2/+3/+5、高强度工作 +1/季），每季度初用文案量表**校准账本**（以观测读数为准，账本只补「读数间隔期」的增量）。

### B2 三级响应（对齐真实触发线 ≥5）
| 账本估算 | 强制动作 |
|---|---|
| ≥ 3 | 当季必排：体力「处理历史埋雷」+ 主行动「低调避险」（−2/季纠正，留 2 点余量） |
| ≥ 4 | **拒收一切 `ΔRisk ≥ +1`** + 连续两季埋雷+避险，直到账本 ≤ 2 |
| 爆雷后 | **冷静期 3 个月**：禁一切 `ΔRisk ≥ +1`，无论缺口多大——**这是 RUN 4 型二次爆雷的直接解药**（首爆后 output 回写、缺口重开，正是 Agent 最想选高风险补偿的时点） |

### B3 常态预算
- 每个大周期（6 个月）累计 ΔRisk 注入 ≤ 2（约等于每季最多吃一次 +1 或直接拒收）。
- 与 C 组的关系：改 1 的「末端 +1 档例外」以**账本 ≤ 3** 为前提，两条款自动兼容。
